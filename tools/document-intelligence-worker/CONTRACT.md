# Local document-intelligence contract

Slice A changes the intake/result envelope; Slice B adds an opt-in document genre gate. Existing candidate extraction, table interpretation and canonical review semantics remain unchanged.

Slice C adds an independent `DocumentIntelligence:SectionObservationsEnabled` option (default `false`). It requires `ContractVersion=2` and `GenreRoutingEnabled=true`. The V2 request then carries `options.sectionObservations=true`. Genre routing still decides whether Award extractors run: only `AWARD` and `SUPPLEMENTARY_AWARD` receive section observations, from the cached all-page OCR source lines. Other and `UNKNOWN` genres return only the genre observation. There is no additional OCR pass or table inference.

Each `DocumentSection` observation has an extensible source-context `semantic`, separate structural `presentation`, `pageStart`/`pageEnd`, optional `rawHeading`, bounded `evidence` (`page`, `rawText`, `sourceRegion`), `confidence`, `requiresHumanReview=true`, `warnings`, and `classifierVersion`. Clear source headings may name sections; ambiguous, unheaded, or unreadable pages become `UNKNOWN` review observations. Multiple or repeated headings stay separate. A section extends across pages only with an explicit continuation cue. Backend validation rejects missing page coverage, unsupported labels, invalid page ranges/regions, missing proof for a known heading, and sections attached to a non-Award genre before staging. The existing ingestion candidate JSON/locator stores `DocumentSection` review items with V2 processing identity; no canonical business fact or new database table is written. Disabling the option restores Slice B's exact one-observation contract. The existing V1 request shape is unchanged.

The existing `DocumentIntelligence:ContractVersion` option defaults to `1`. Set it to `2` to opt the Award-linked local worker path into the versioned envelope; unsupported values fail before launch. Existing V1 worker requests/results and historical ingestion sessions remain readable. The same `LocalDocumentIntelligenceClient`, `AwardPdfExtractionService` and ingestion path are used for both versions. NM clients continue to send V1 unless explicitly opted in later.

V1 request/result retains its current shape. Extra nullable intake keys are ignored by the V1 worker; V1 output does not gain V2 fields. V2 request requires `contractVersion=2`, existing `documentId`, `documentVersion` (positive), `physicalSha256` (full SHA-256 of the stored PDF), and `pageCount` (full PDF count), alongside the existing path/Award context. The backend hashes the physical file and checks a stored `Document.Sha256Hash` when present, independently counts PDF pages, and sends the verified values. The worker checks the hash again **before OCR** and checks its opened PDF page count. The backend rehashes after processing to detect source mutation.

V2 response retains `documentId`, `status`, `pagesProcessed`, `candidates`, `warnings` and `metrics`, and adds `physicalSha256`, `documentVersion`, `pageCount`, `processedAt` (UTC), `extractorVersion`, `errors` and `observations`. Without genre routing, `observations` remains empty; unsupported observation types fail closed. `pagesProcessed` may be lower than `pageCount` only for an intentional selected-page request outside genre routing; `Partial` is **not** a successful status. Candidate payloads stay unchanged. Version/SHA/page/processing metadata is copied into each V2 candidate's source locator. The existing job persists total page count, completion time and `contract-2:<extractorVersion>`; `Document` already stores SHA and version. No new database column or migration is needed for Slices A or B.

Set `DocumentIntelligence:ContractVersion=2` and `DocumentIntelligence:GenreRoutingEnabled=true` together to enable Slice B. V1 and V2 without genre routing retain their previous behavior. Genre routing reads OCR headings and introductory source lines across **all** pages before Award extraction. Filename, Award link, village, and stored DocumentType are never classifier inputs. The extensible routing labels currently supported are `AWARD`, `SUPPLEMENTARY_AWARD`, `POSSESSION_PROCEEDINGS`, `CLAIMANT_REGISTER_OR_CONTINUATION`, `RENTAL_OR_REQUISITION_OFFER`, `OTHER`, and `UNKNOWN`. Weak or conflicting source cues produce `UNKNOWN`.

With the gate enabled, exactly one `DocumentGenre` observation is required. It contains `genre`, `confidence`, `requiresHumanReview`, `page`, bounded `evidence[]` (`page`, `rawText`, optional `sourceRegion`), `warnings[]`, and `classifierVersion`. The backend validates every field and stages one reviewable `DocumentGenre` candidate in the existing ingestion session. The source locator retains the evidence and V2 processing identity. Only `AWARD` and `SUPPLEMENTARY_AWARD` run existing Award extractors; every other genre, including `UNKNOWN`, stages only the genre observation. No genre decision creates a canonical Award fact. The existing Workbench can list this review item through the generic queue; dedicated genre correction controls belong to a later slice.

Failures are visible and fail closed: disabled/missing worker preflight, invalid JSON, missing V2 identity, unsupported/mismatched version, hash or page mismatch, worker nonzero exit, `Failed`/`Partial` status, or unsupported nonempty observations all prevent staging. Worker stderr is sanitized by the existing client. An OCR/page failure aborts the run rather than returning fabricated successful candidates. Legacy V1 behavior remains the rollback path by setting `ContractVersion=1`.
